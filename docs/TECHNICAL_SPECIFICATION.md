# Log Incident Analyzer — техническое задание

**Версия документа:** 1.0 · **Дата:** 27 сентября 2026 года

**Рабочее имя проекта:** Log Incident Analyzer, сокращённо LIA

**Назначение:** GitHub-портфолио для SOC L1 / Blue Team / Detection Engineering, с демонстрацией Python-разработки.

**Статус:** спецификация будущей реализации. Программа и автоматизированные тесты ещё не реализованы; численные показатели ниже являются целями приёмки.

## Как пользоваться документом

Документ определяет обязательную версию v1.0, промежуточный MVP и отдельное развитие после релиза. Он рассчитан на одного разработчика. Сначала реализуются контракты данных и небольшой сквозной сценарий, затем остальные детекты и проверка качества.

Сопутствующие материалы: [TEST_PLAN.md](TEST_PLAN.md) — стратегия и 256 тест-кейсов; [test-cases.json](test-cases.json) — те же кейсы в машиночитаемом виде. Это требования к будущим тестам, а не отчёт об их прохождении.

Термины **должен**, **обязательно**, **P0** обозначают обязательные требования. **P1** обозначает обязательное для v1.0 после завершения MVP. **P2** — развитие вне приёмки v1.0. Приоритет теста обозначает риск проверяемого поведения, а не этап реализации.

## 1. Продукт и его отличие

### 1.1. Задача

Разработать локальный инструмент, который получает журналы веб-приложения, обнаруживает признаки атак на аккаунты и подозрительной веб-активности, объединяет связанные срабатывания и готовит карточку первичного расследования для аналитика SOC L1.

На выходе пользователь получает:

1. Список случаев, требующих проверки, с приоритетом и объяснением.
2. Хронологию и ссылки на события, подтверждающие каждое утверждение.
3. Альтернативные объяснения: ошибка пользователя, NAT, восстановление доступа, разрешённое сканирование.
4. Ограничения вывода и перечень недостающих данных.
5. Рекомендуемые действия аналитика и условия передачи на L2.
6. Отчёт о качестве логов и применимости каждого правила.

### 1.2. Центральная идея для портфолио

**Объяснимый первичный анализ атак на аккаунты с проверкой достаточности телеметрии и воспроизводимой оценкой ложных срабатываний.**

Отличие демонстрируется на одной истории в трёх вариантах: подозрительная последовательность входов; похожая легитимная активность с подтверждающим контекстом; та же история с неполными логами. Пользователь видит, как меняются вывод, приоритет и границы уверенности.

Уникальность в масштабе всей отрасли не заявляется. Ценность проекта — законченная реализация, понятные решения и проверяемые результаты.

### 1.3. Пользователи

- Аналитик L1: получить первичный разбор и доказательства.
- Detection engineer: изменить правило, проверить его на сценариях и увидеть регрессию.
- Разработчик приложения: узнать, каких полей и событий не хватает для расследования.
- Ревьюер GitHub-проекта: запустить демонстрацию и проверить заявленные результаты.

### 1.4. Границы ответственности

Алерт означает выполнение условия детекта. Кейс объединяет связанные алерты. Подтверждённый инцидент — результат решения человека с дополнительными данными. Анализатор не должен автоматически объявлять компрометацию, блокировать пользователей, менять настройки MFA или отправлять сообщения во внешние системы.

- Ограниченный импорт Sigma через адаптер с опубликованной таблицей совместимости.

## 5. Входные данные

### 5.1. Поддерживаемые источники

**app-audit-v1:** JSONL, одна JSON-запись на строку. Обязательные поля: `schema_version`, `event_id`, `timestamp`, `action`, `outcome`. Идентификатор источника, tenant и приложение поступают из проверенного манифеста импорта. Дополнительные поля зависят от действия.

Поддерживаемые действия: `auth.login`, `auth.mfa.challenge`, `auth.mfa.enroll`, `auth.password.reset`, `authz.check`, `http.request`, `source.heartbeat`. Результаты: `success`, `failure`, `denied`, `requested`, `unknown`. Разрешённые пары action/outcome определяются JSON Schema. Например, MFA challenge/requested не является login/success; source.heartbeat/success используется только для проверки заявленного покрытия.

**nginx-json-v1:** фиксированный документированный `log_format` с `escape=json`: ISO-время с зоной, peer IP, method, URI path, status, request_id. Заголовки авторизации, cookie, тело и query string по умолчанию не включаются. Конфигурация логирования входит в примеры. Возможность JSON-экранирования описана в [документации Nginx](https://nginx.org/en/docs/http/ngx_http_log_module.html).

**nginx-combined-v1:** строго определённый стандартный combined-формат; дополнительные поля произвольного формата требуют другого адаптера. Поле remote_user само по себе не доказывает идентичность пользователя приложения. HTTP 200/302 не преобразуется в успешный вход.

Пример исходного события app-audit-v1; имена учётных записей синтетические. actor.user_id при failure — заявленный аккаунт, а не установленная личность отправителя:

```json
{
  "schema_version": "app-audit-v1",
  "event_id": "demo-auth-0001",
  "timestamp": "2026-01-15T12:00:00.000000Z",
  "action": "auth.login",
  "outcome": "failure",
  "actor": {"user_id": "demo-user"},
  "network": {"peer_ip": "192.0.2.10"},
  "reason_code": "invalid_credentials"
}
```

Поддержка сжатия: только одиночный gzip-поток. ZIP/TAR/7z и несколько gzip-members в одном файле в v1.0 отклоняются явной ошибкой. UTF-8; BOM разрешён только в начале файла. Ошибочная кодировка фиксируется без тихой замены байтов.

### 5.2. Манифест импорта

Манифест содержит относительные пути внутри разрешённого каталога, format, source_id, tenant_id, application_id, необязательную timezone, declared_capabilities, authority, clock_offset_ms и clock_uncertainty_ms. Настройки фиксируются в manifest hash. Минимальный single-tenant режим использует явные значения `local`/`demo`, а не NULL.

Capability — декларация оператора о том, что источник способен записывать определённые поля/действия. Она не доказывает полноту наблюдения. Для справки сохраняются начало и конец заявленного периода выгрузки; без этой информации отсутствие событий нельзя считать остановкой журналирования.

Начальный словарь capabilities: `auth.login.failure`, `auth.login.success`, `auth.mfa.challenge`, `auth.mfa.enroll`, `authz.denied`, `http.request`, `source.heartbeat`; отдельно перечисляются available_fields в нормализованной схеме после адаптера. Authority: `application_audit`, `idp_audit`, `web_access`, `unverified`. Это заявленные свойства источника, а не криптографическая аттестация.

Пример source manifest:

```yaml
schema: lia-input/v1
input_root: ./data
sources:
  - path: app.jsonl
    format: app-audit-v1
    source_id: demo-app-audit
    tenant_id: local
    application_id: demo
    authority: application_audit
    platform_scope: generic_application
    declared_capabilities: [auth.login.failure, auth.login.success]
    available_fields: [actor.user_id, network.client_ip]
    clock_offset_ms: 0
    clock_uncertainty_ms: 0
```

`input_root` разрешается относительно файла манифеста; source path — относительно input_root. Effective manifest перед хешированием канонизируется: entries сортируются по source_id/path, map keys — по имени, значения defaults развёрнуты. Это обеспечивает независимость от порядка перечисления файлов. Абсолютный путь рабочего каталога не входит в аналитический hash.

Пути не берутся из содержимого логов. Для v1.0 обрабатываются обычные локальные файлы, перечисленные в манифесте. Symlink и Windows reparse point отклоняются; сетевые пути не поддерживаются. Input-каталог монтируется в контейнер read-only.

### 5.3. Ограничения по умолчанию

- Строка: до 256 KiB включительно до декодирования; превышение — ошибка записи.
- Вложенность JSON: до 16 уровней; неизвестные поля отбрасываются с агрегированным счётчиком.
- Одна строка нормализованного поля: до 4096 символов; превышение обязательного поля отклоняет запись, необязательного — обнуляет поле с причиной.
- До 100 файлов и до 2 GiB суммарного распакованного входа на run.
- До 100 000 одновременно активных group keys на правило; до 16 GiB рабочих файлов на workspace. При превышении — контролируемый failed, без удаления уже обнаруженных проблем из диагностики.
- Для gzip: остановка при превышении абсолютного лимита; ratio > 100:1 после первых 10 MiB распаковки также останавливает run.
- Лимиты настраиваются явно и записываются в manifest. На превышении размера всего run результат считается незавершённым; успешный отчёт не публикуется.

Пустой корректный файл допустим и даёт `no_data`. Неподдерживаемый источник — ошибка конфигурации. Битая запись в допустимом источнике — quarantine с безопасными метаданными, остальные строки обрабатываются.

Учёт физических строк: `rows_seen = accepted_unique + duplicate_rows + quarantined_rows + conflicted_rows + blank_rows`. Категории взаимоисключающие. Конфликт ID переводит все конфликтующие строки в conflicted_rows до фиксации run. У идентичной повторной копии артефакта отдельно учитывается reused_artifacts; строки одного логического артефакта не пересчитываются как новые. Пустые строки имеют длину ноль после удаления только разделителя строки; пробельная строка не считается валидным JSON.

## 6. Нормализованная модель

Общая схема компактная и версионируемая; название поля не означает совместимость с ECS/OCSF. Экспорт в внешние схемы — отдельный адаптер.

| Группа | Поля и правила |
|---|---|
| Идентичность | `event.uid`, `event.original_id`, `schema.version`, `source.id`, `tenant.id`, `app.id` |
| Время | `event.time_utc`, `event.time_original`, `event.time_precision_ms`, `event.time_uncertainty_ms` |
| Семантика | `event.action`, `event.outcome`, `event.category`, `event.reason_code` |
| Субъекты | `actor.user_id`, `target.user_id`, `actor.role`, `target.resource_id`; NULL означает неизвестное |
| Сеть | `network.peer_ip`, `network.client_ip`, `network.client_ip_basis`, `network.ip_family` |
| HTTP | `http.method`, `http.path`, `http.status`, `http.request_id`; query по умолчанию исключён |
| Авторизация | `auth.session_ref`, `auth.mfa_request_id`, `auth.factor_kind`, `auth.device_ref` |
| Качество | `quality.flags`, `quality.missing_fields`, `source.authority` |
| Происхождение | `artifact.sha256`, `source.line_number`, `source.byte_offset`, `record.digest` |

`event.original_id` уникален в пределах source/tenant/app. `event.uid` для app-audit вычисляется из этой области и original_id. Совпадающий ID с различающимся нормализованным содержимым — конфликт: обе версии исключаются из анализа текущего run, выводится quality issue. Нельзя молча выбирать последнюю.

Для Nginx без event_id идентичность записи определяется хешем файла и номером строки. Копия того же файла распознаётся как тот же артефакт. Одинаковые строки в разных файлах без устойчивого ID автоматически не схлопываются: возможный дубль показывается в качестве данных. Не следует терять реальные повторные HTTP-запросы.

`actor.user_id` для входа обозначает заявленный идентификатор аккаунта; ошибка входа не доказывает, кто отправил запрос. Для изменения MFA actor и target хранятся отдельно. При совпадении строковых имён разные tenant/app остаются разными сущностями.

### 6.1. Нормализация

- Время хранится как UTC с целочисленной точностью микросекунд; исходная точность сохраняется отдельно.
- Без зоны используется только timezone манифеста. DST-неоднозначность без явного offset/fold отклоняется.
- Clock offset применяется один раз с сохранением исходного значения; неопределённость не исчезает после коррекции.
- IPv4/IPv6 канонизируются библиотекой IP-адресов. IPv4-mapped IPv6 приводится к IPv4 по опубликованному правилу.
- Имена аккаунтов сохраняют регистр и Unicode. Case folding включается только профилем конкретного источника.
- Строки `null`, `-`, пустая строка не становятся универсальным user ID. Правила преобразования определяет адаптер.
- Статусы и enum проверяются строго; строка `"false"` не преобразуется в boolean true.
- Для path сохраняются безопасное исходное представление и нормализованная версия. Query отделяется до percent-decoding. Выполняется максимум один проход decoding; slash и dot-segments не переписываются по догадке.
- User agent и URL относятся к недоверенным данным. Ссылки из событий не открываются автоматически.

### 6.2. Peer IP и forwarded-заголовки

По умолчанию client_ip равен peer_ip. Forwarded/X-Forwarded-For учитывается только для peer из заданных trusted_proxy_cidrs и при включённом профиле, который гарантирует перезапись/добавление заголовка прокси. Цепочка обходится справа налево с отбрасыванием известных доверенных прокси. Некорректная цепочка даёт peer_ip и quality flag. Значение из тела события не может изменить список доверенных прокси.

### 6.3. Секреты и происхождение

Persisted event строится по allowlist полей. Пароли, bearer-токены, cookie и сырые идентификаторы сессий не сохраняются. Допустимый session_ref — уже безопасный идентификатор либо HMAC от исходного значения с ключом workspace. Ключ не попадает в отчёты; его идентификатор входит в manifest. Для повторяемости используется тот же ключ. Потеря ключа означает невозможность воспроизвести прежние pseudonyms.

Оригинальные файлы не изменяются и не копируются в публичный отчёт. Quarantine хранит source/line/digest/error code, без сырой строки. SHA-256 подтверждает совпадение с ранее посчитанными байтами; он не подтверждает подлинность источника и не защищает от атакующего, способного переписать и файл, и манифест.

## 7. Время, окна и повторяемость

1. v1.0 выполняет пакетный анализ завершённой выгрузки. Позднее поступившие данные анализируются новым run; автоматического streaming watermark нет.
2. Перед детектированием события сортируются по `(event.time_utc, event.uid)`. Второй ключ обеспечивает воспроизводимость, но не доказывает причинный порядок.
3. Для окна W с опорной точкой t используются события `t-W < event.time_utc <= t`. Левая граница исключается, правая включается.
4. Для каждого события-кандидата оценивается окно. Кандидатные срабатывания одного правила и group key с пересекающимися evidence объединяются в alert episode.
5. Чтобы непрерывная активность не создавала бесконечный episode, максимальная длительность — 60 минут. При первом кандидате за пределом этого интервала создаётся следующий episode; повторяющиеся evidence допустимы и явно связаны.
6. DET-003 использует qualifying window DET-001, закончившееся строго раньше успешного входа, и не дальше 10 минут от него. Все доказательства этого window должны предшествовать успеху. Из нескольких подходящих окон выбирается последнее, при равенстве — стабильный ID.
7. DET-006 связывает конкретное успешное событие DET-003 с enrolment строго позже него и не дальше 15 минут. Требуется одинаковый непустой session_ref и совпадающие tenant/app/user.
8. Для строгого порядка интервалы неопределённости времени не должны пересекаться: верхняя граница предыдущего события меньше нижней следующего. Для источника с усечением времени, точностью p микросекунд и uncertainty u интервал равен `[t-u, t+u+p-1us]`. Например, секундная точность охватывает всю записанную секунду. Адаптер обязан объявить способ округления; неизвестный способ даёт order_unverified. При пересечении интервалов последовательность получает `order_unverified`, без DET-003/006. События и счётные детекты сохраняются.
9. Для count-детектов время оценивается по скорректированной точке; quality flag отмечает неопределённость. Если clock_uncertainty превышает 30 секунд, событие исключается из временных детектов и учитывается как неоценённое.
10. Alert ID зависит от rule ID/version, group key и первого candidate ID episode. Case ID зависит от отсортированного набора alert IDs. Сравнение run с разными данными выполняется по связям evidence и ключам, а не обещанию неизменного case ID.

Для детерминированного сравнения формируется `analysis.json` без текущего времени, абсолютных путей, random UUID и длительности выполнения. Операционные сведения вынесены в `run.json`. Повтор на одинаковых данных, конфигурации, context, reference snapshot и ключе псевдонимизации должен давать одинаковый analysis hash.

### 8.1. Дополнительные условия

- DET-001/002/004 считают только явные ошибки проверки входа. Сетевые 5xx, captcha challenge и MFA deny не являются такими ошибками.
- DET-002 показывает число ошибок на аккаунт и отношение success/failure как факты, но не исключает детект из-за одной дополнительной ошибки. Нельзя делать правило немонотонным без обоснованного теста.
- DET-005 считает разные request_id. Пять повторных записей одного challenge дают один запрос. Без request_id правило недоступно для этих событий.
- DET-006 требует target.user_id = пользователь DET-003. Если actor отличается, это отдельный контекст административного изменения, и автоматическая цепочка v1.0 не создаётся. device_ref должен обозначать зарегистрированное устройство, а не его публичное отображаемое имя.
- DET-007 использует список из конфигурации, например `/.env`, `/.git/config`, `/admin`, `/backup.zip`, `/config`. Список — данные правил. Повтор одного пути не даёт пять разных путей. Любой HTTP-статус учитывается; ответ отображается в evidence.
- DET-008 не выводит существование уязвимости из последовательности denied. Успешное обращение к чужому ресурсу требует отдельной информации о владельце и политике доступа, вне v1.0.

### 8.2. ATT&CK mapping

Для каждой привязки хранить technique_id, URL, snapshot/version, platform_scope, rationale, evidence requirements и `mapping_status=candidate|supported_behavior`. Ни одно значение не означает подтверждённую атаку.

| Детект | Привязка | Обоснование и граница |
|---|---|---|
| DET-001 | [T1110.001 Password Guessing](https://attack.mitre.org/techniques/T1110/001/) | Наблюдается серия неуспешных попыток против аккаунта; намерение неизвестно |
| DET-002 | [T1110 Brute Force](https://attack.mitre.org/techniques/T1110/), кандидат [T1110.003 Password Spraying](https://attack.mitre.org/techniques/T1110/003/) | Широкий охват аккаунтов согласуется со spraying, но равенство паролей не наблюдается |
| DET-003 | Наследует T1110.001 от исходного детекта | Успех — дополнительный факт; сам по себе не обосновывает Valid Accounts |
| DET-004 | [T1110 Brute Force](https://attack.mitre.org/techniques/T1110/) | Несколько источников; подтип по этим данным не доказан |
| DET-005 | [T1621 MFA Request Generation](https://attack.mitre.org/techniques/T1621/) | Серия запросов к MFA; соблюдается применимость к наблюдаемой системе |
| DET-006 | [T1098.005 Device Registration](https://attack.mitre.org/techniques/T1098/005/) | Регистрация MFA-устройства в IdP; для произвольного локального приложения mapping остаётся пустым, если platform_scope не подходит |
| DET-007/008 | По умолчанию пусто | Наблюдаемых веб-событий недостаточно для однозначной привязки |

ATT&CK описывает поведение противника; OWASP используется как источник требований к журналированию и контекста веб-безопасности. Автоматического соответствия «один HTTP-паттерн = одна категория OWASP = одна техника ATT&CK» нет.

Справочник ATT&CK должен храниться как локальный минимальный snapshot с датой и источником; обновление выполняется отдельной явной командой/процедурой разработчика. Обычный анализ не обращается в сеть. Отключённые или устаревшие ID вызывают предупреждение при валидации правил. Не вычислять процент покрытия всей ATT&CK по числу тегов.

### 8.3. Собственный DSL правил

v1.0 использует `lia-rule/v1`. Формат вдохновлён декларативными правилами; он не называется Sigma-совместимым. Поддержка ограничена `event_count`, `distinct_count`, `multi_count`, `sequence`.

Разрешены проверки equals, in, exists, cidr_match, starts_with и явные all/any/not. Пользовательские regex, Python, shell, Jinja и сырой SQL в правиле запрещены. Многошаговые зависимости образуют DAG; циклы отклоняются до анализа. NULL обрабатывается трёхзначно: сравнение с отсутствующим полем даёт UNKNOWN; NOT UNKNOWN остаётся UNKNOWN; отбор принимает только TRUE. `exists` проверяет непустое валидное значение.

```yaml
schema: lia-rule/v1
id: DET-001
version: 1
title: Repeated failed sign-ins
status: stable
description: Repeated failed authentication attempts for one account and source
rationale: The observed pattern warrants review for possible password guessing
owner: project-maintainer
references: [https://attack.mitre.org/techniques/T1110/001/]
tests: [D01-001, D01-002, D01-003, D01-004, D01-005, D01-006, D01-007, D01-008]
required_capabilities: [auth.login.failure]
required_fields:
  - actor.user_id
  - network.client_ip
select:
  all:
    - field: event.action
      equals: auth.login
    - field: event.outcome
      equals: failure
aggregate:
  type: event_count
  group_by: [tenant.id, app.id, actor.user_id, network.client_ip]
  window: 5m
  threshold: {gte: 10}
severity: medium
attack:
  - technique_id: T1110.001
    mapping_status: candidate
false_positives:
  - Repeated mistakes by the account owner
next_steps:
  - Verify whether the account owner recognizes the activity
```

Полная schema должна требовать description, rationale, owner, references, tests, severity, version, required_capabilities, false_positives, next_steps. Пример выше задаёт контракт первого правила. Остальные правила используют тот же metadata contract. Неизвестные ключи, дубли YAML-ключей и повтор rule ID — ошибка. Версия — положительное целое. Все group_by должны включать tenant/app; отсутствие приводит к ошибке валидации.

### 8.4. Контракт агрегатов

- `event_count`: число уникальных event.uid в окне; threshold — один оператор gte с положительным integer.
- `distinct_count`: aggregate.field указывает поле для distinct; NULL не учитывается. Используется DET-002, DET-005, DET-007.
- `multi_count`: список именованных measures (`events`, `distinct_ips`, `distinct_resources`) и conjunction порогов gte; применяется DET-004/008. Все measures используют один отфильтрованный набор событий и одно окно.
- `sequence`: upstream detector ID, select следующего события, match_fields, max_gap, strict_order=true и выбор latest_qualifying_window. Применяется DET-003/006. Зависимости должны быть ацикличными; функция не опирается на порядок строк входного файла.
- Операторы equals/in сравнивают значения одного типа; неявного преобразования `"10"` в 10 нет. Starts_with чувствителен к регистру. Cidr_match принимает только нормализованный IP и валидную CIDR-сеть.
- Поля, доступные в фильтрах и measures, перечислены в schema. Aggregate SQL строится из AST с allowlist операций; пользовательский SQL не принимается.
- `all([])` и `any([])` запрещены схемой. Максимальная глубина AST — 8, число узлов — 1000, число правил — 100; превышение отклоняется до обработки событий.

Нулевое число matches при ready — нормальный результат работы правила. Не следует смешивать его с unavailable, когда правило не удалось оценить.

## 9. Кейсы, контекст и решение L1

### 9.1. Связи

DET-001/003/006 связываются по явным зависимостям и shared evidence. Остальные алерты объединяются в кейс, если совпадают tenant/app, непустой user и пересекается интервал активности с допуском 15 минут. Максимальная длина кейса — 60 минут от первого алерта; последующая активность образует связанный кейс.

Алерты DET-002/007 без единственного user группируются отдельно по правилу и client_ip. Они могут отображаться как related к пользовательскому кейсу только при наличии совпадающего evidence. Один общий IP, строка user agent или географическая метка не создаёт причинную связь. Рёбра связи хранят reason и evidence IDs.

### 9.2. Приоритет

Severity принадлежит правилу. Priority принадлежит кейсу. В v1.0 используется опубликованная дискретная политика:

- База: low=20, medium=40, high=60; взять максимум среди алертов кейса.
- +15: критический аккаунт/приложение из проверенного context-файла.
- +15: подтверждённая по данным последовательность DET-006.
- −20: разрешённая работа с совпадающими rule ID, actor/target, областью и временным интервалом.
- Ограничить score диапазоном 0–100. Low <30; medium 30–59; high 60–79; critical ≥80.

Добавка учитывается один раз на кейс. Дубли и дополнительные одинаковые алерты не наращивают score. Корпоративный NAT, знакомый IP или успешная MFA сами по себе score не уменьшают. Разрешённые работы не удаляют evidence. Результат расчёта показывает каждое слагаемое.

`confidence` — категориальное качество опоры на данные, не вероятность атаки: `limited`, `supported`. Для supported все evidence валидны, нужные поля присутствуют, порядок доказуем там, где нужен, и authority соответствует профилю. При любом из этих нарушений limited; причина обязательна. Проблемы времени, при которых сам детект невозможен, ведут к отсутствию этого детекта и quality issue, а не к выдуманному low-confidence алерту.

### 9.3. Предварительное решение

- `review`: алерт требует проверки.
- `escalate`: priority high/critical; либо DET-006 независимо от понижения по контексту. Это рекомендация, не отправка данных.
- `insufficient_data`: правило/цепочка не оценены из-за отсутствующих данных; оформляется quality finding, без утверждения о безопасности.

Автоматического benign/false_positive нет. Аналитик может вручную закрыть кейс с причиной `benign_activity`, `false_positive`, `confirmed_incident`, `inconclusive`. При высоком приоритете закрытие требует непустого обоснования, но не внешнего подтверждения в приложении.

### 9.4. Контекст

JSON/YAML-файл содержит аккаунты и критичность, приложения, NAT-сети, trusted proxies, approved maintenance. Каждая запись имеет source, author, reason, created_at, valid_from, expires_at и область. Интервал применимости `[valid_from, expires_at)` оценивается по event time. Манифест хранит hash контекста.

Подавление алерта — отдельное явное правило с точным detector ID и областью. По умолчанию подавленный алерт остаётся в результатах с `suppressed=true` и suppression_id; стандартная очередь скрывает его, счётчики и экспорт учитывают отдельно. Нельзя подавлять все события одного tenant неявным wildcard. DET-006 может быть помечен suppression, но остаётся видимым в очереди high-risk и рекомендует проверку.

### 9.5. Статусы и заметки

Статусы кейса: new → in_review → escalated/closed; closed можно reopen в in_review. Каждый переход хранит старое/новое значение, analyst label, время и причину. Label локального пользователя не считается проверенной идентичностью. Заметки не изменяют детекторные факты. Новые run сохраняют историю старых кейсов; автоматического переноса вердикта между изменившимися кейсами нет.

## 10. Отчёт о достаточности телеметрии

Для каждого правила показывать `ready`, `degraded`, `unavailable` или `no_data`.

- ready: необходимые capabilities заявлены, все подходящие записи имеют поля, качество времени допустимо.
- degraded: часть подходящих записей исключена или capabilities не заявлены, хотя часть событий пригодна.
- unavailable: в непустой выгрузке нет источника/полей для запуска правила.
- no_data: источник с заявленными capabilities присутствует, но в нём нет подходящих событий; это не гарантия отсутствия атак.

Приоритет определения: отсутствие необходимых источников → unavailable; подходящих событий нет при наличии capabilities → no_data; пригодная часть неполна → degraded; иначе ready. Если подходящие события есть, но среди них нет ни одного пригодного для правила, статус unavailable с числом исключённых. Незаявленные capabilities дают degraded при наличии пригодных событий.

Для каждого обязательного поля считать denominator как число событий нужной категории до фильтра поля, missing/invalid counts и процент пригодности. Событие без user может быть непригодно для DET-001 и пригодно для DET-007. Нельзя удалять его из всего анализа из-за одного правила.

Примеры рекомендаций: добавить результат авторизации; записывать безопасный session_ref для последовательностей; сохранять отдельный event ID; включить события регистрации MFA; указать зону времени; корректно настроить доверие к forwarded-заголовкам.

Проверка остановки логирования допустима только при заданных coverage interval и ожидаемом heartbeat. В v1.0 отсутствие строк вне такого контракта называется отсутствием наблюдений. Отчёт не выдаёт сертификат соответствия OWASP.

Для heartbeat контракт задаёт UTC `coverage_start`, `coverage_end`, `expected_interval_s` и `max_gap_s`; значения положительны, max_gap не меньше expected_interval. Проверяются разрывы между heartbeat и границами заявленного интервала. Разрыв строго больше max_gap даёт quality finding `heartbeat_gap`; ровно max_gap допустим. В демонстрации interval=60s, max_gap=180s. Finding означает пробел наблюдения: причины остановки источника, доставки или экспорта по одним логам не различаются.

## 11. Архитектура и стек

### 11.1. Рекомендуемый стек

- Python 3.12+; обязательная CI-матрица 3.12 и 3.13 на Linux, smoke на Windows.
- `uv` и lockfile; `pyproject.toml`; зависимости с ограниченными диапазонами и зафиксированным разрешением.
- Typer для CLI, Pydantic v2 для моделей и проверок, стандартный sqlite3 для хранения.
- YAML safe loader с запретом пользовательских тегов, aliases и дублированных ключей.
- Jinja2 с autoescape для HTML; HTML содержит локальный CSS и не требует JavaScript.
- pytest, pytest-cov, Hypothesis; Ruff и mypy; инструмент проверки зависимостей.
- Docker для повторяемой демонстрации; GitHub Actions для CI.

Это проектный выбор; совместимость конкретных зависимостей проверяется первым implementation spike и фиксируется в lockfile. Основания: [Pydantic](https://docs.pydantic.dev/latest/), [sqlite3](https://docs.python.org/3/library/sqlite3.html), [Jinja](https://jinja.palletsprojects.com/en/stable/api/), [pytest](https://docs.pytest.org/en/stable/how-to/parametrize.html), [Hypothesis](https://hypothesis.readthedocs.io/en/latest/).

### 11.2. Поток обработки

```text
Манифест + файлы + контекст + правила
  → проверка конфигурации и лимитов
  → чтение / распаковка / парсинг
  → нормализация / исключение секретов / quality findings
  → SQLite events + provenance
  → сортировка по времени / правила / alert episodes
  → связи / кейсы / приоритет / рекомендации
  → analysis.json + отчёты + run.json

Эталонные метки сценариев → evaluator → metrics.json
                          (метки не попадают в детектор)
```

## 12. Хранилище и обработка ошибок

Таблицы: schema_migrations, runs, artifacts, artifact_occurrences, events, event_provenance, quality_findings, alerts, alert_events, cases, case_alerts, case_relations, case_notes, case_history, suppressions. Все таблицы с данными содержат область run/tenant/app или внешние ключи, через которые она однозначно определяется. Foreign keys включены и проверяются.

Индексы: `(tenant, app, action, time)`, `(tenant, app, user, time)`, `(tenant, app, client_ip, time)`, event UID и artifact hash. Выбор дополнительных индексов подтверждается benchmark, без требования индексировать каждое поле.

Run states: created, ingesting, analyzing, completed, completed_with_warnings, failed, interrupted. Один writer на workspace; второй запуск завершается понятной ошибкой занятости. У каждого run отдельная staging-область. Результаты публикуются атомарно после успешной транзакции и экспорта. Частичные файлы имеют временное имя и не открываются как завершённый отчёт.

Повторный импорт артефакта не удваивает события, но сохраняет информацию о повторной попытке. Не поддерживать незаметное продолжение изменившегося входа. Изменение файла во время чтения определяется повторной проверкой характеристик и digest; run останавливается с `input_changed`.

При Ctrl+C сохранить статус interrupted, закрыть БД и удалить только временные файлы текущего run. Код 130. В v1.0 возобновление — новый run с идемпотентным импортом; частичный анализ не выдаётся за полный.

Quarantine >0 означает completed_with_warnings и ненулевой код частичной обработки. Число повреждённых строк и их источники обязательно показываются. Сбой диска, целостности БД, лимита общего объёма или конфигурации означает failed. Нельзя возвращать пустой «успешный» отчёт при аварии.

## 13. CLI-контракты

Все команды ниже — целевой интерфейс будущей реализации.

```bash
lia validate-config --config config.yml
lia validate-rules --rules rules/
lia analyze --manifest examples/demo/manifest.yml --config config.yml --output reports/demo
lia explain --run reports/demo --case CASE_ID --format markdown
lia quality --run reports/demo --format json
lia case set-status --run reports/demo --case CASE_ID --status in_review --analyst local-user --reason "Started review"
lia case add-note --run reports/demo --case CASE_ID --text "User confirmation pending" --analyst local-user
lia case set-status --run reports/demo --case CASE_ID --status closed --verdict benign_activity --analyst local-user --reason "Approved recovery verified"
lia replay --suite datasets/evaluation/manifest.yml --output reports/evaluation
lia compare --baseline reports/baseline --candidate reports/candidate --output reports/comparison
lia benchmark --profile benchmarks/standard.yml --output reports/benchmark
lia demo --output reports/demo
```

`analyze` по умолчанию сохраняет JSON и Markdown. `--formats json,markdown,html` включает HTML. Существующий непустой output не перезаписывается; новый run либо отдельный путь. Команда compare отклоняет разные dataset hash; изменения правил/context разрешены и показываются.

`replay` читает scenario labels только evaluator-компонентом. `demo` работает с локально включённым набором. Никакая из этих команд не отправляет данные, не запускает вредоносные инструменты и не атакует сеть.

Коды выхода: 0 — завершено; 2 — аргументы/схема/конфигурация; 3 — частично обработано или нарушен `--require-complete`; 4 — I/O, ресурсный лимит, БД, внутренняя ошибка; 10 — полностью завершённый анализ с алертами, только при `--fail-on-alert`; 130 — прерывание. При сочетании состояний ошибка/частичность имеют приоритет над 10. `--require-complete` требует ready для явно включённых правил; default допускает degraded/unavailable с предупреждением.

`--json` означает один JSON-объект в stdout и отсутствие progress bar; диагностические сообщения — stderr. В обычном режиме допустим прогресс. Полный traceback включается только `--debug`, после очистки секретов. Пути с пробелами и Unicode поддерживаются.

## 14. Форматы результата

### 14.1. Файлы run

- `analysis.json`: стабильный версионированный результат, кейсы, алерты, evidence и quality summary.
- `run.json`: версии, hashes, параметры, длительность, counters, состояние, platform, pseudonym key ID.
- `report.md`: краткая сводка и карточки кейсов.
- `report.html`: самодостаточный статический отчёт без внешних ресурсов.
- `quality.json`: готовность правил, распределения пропусков и безопасные диагностические записи.
- `analysis.sqlite`: локальное хранилище, в публичный репозиторий не коммитится.

Необходима JSON Schema для каждого публичного формата; major-версия меняется при несовместимом контракте. JSON и SQLite могут содержать чувствительные идентификаторы; публикация выполняется только через `--shareable`, который псевдонимизирует user/IP/device и удаляет локальные пути. Сохраняются равенство сущностей внутри отчёта, порядок и счётчики. Shareable не обещает абсолютную анонимность любых произвольных входов; встроенные демо используют только синтетические данные.

### 14.2. Карточка кейса

Обязательные поля: ID, заголовок, интервал UTC, tenant/app, сущности, status, severity, priority с расчётом, confidence и причины, факты, гипотезы, альтернативные объяснения, недостающие данные, ATT&CK с обоснованием, хронология, evidence IDs, следующие проверки, критерий эскалации, suppressed/context, версии правил.

У каждого факта есть `evidence_ids`; у гипотезы — rationale и ограничения; у рекомендации — действие человека и ожидаемый источник дополнительной информации. Система не утверждает, что пользователь подтвердил действие, если в context/заметках этого нет. Связь analyst note с фактом обозначается отдельно от логовых доказательств.

Длинные кейсы: максимум 50 событий в карточке и ссылка-якорь на приложение отчёта; полный evidence доступен в JSON/SQLite. Усечение всегда обозначено. HTML имеет оглавление, таблицы с заголовками, читаемый контраст, доступность с клавиатуры и печатный стиль. Цвет дополняет текстовые метки. Фильтры, графики и SPA не обязательны.

## 15. Безопасность самого анализатора

Модель угроз: атакующий может управлять строками логов и полями HTTP, предоставить повреждённые файлы и попытаться вызвать переполнение ресурсов. Оператор управляет конфигурацией, но ошибки в ней всё равно валидируются. ОС и Python runtime считаются доверенными.

Обязательные меры:

1. Никаких eval/exec/shell для содержимого логов и правил; SQL-запросы параметризованы, имена полей берутся из allowlist.
2. Безопасная загрузка YAML, лимиты глубины/размера, запрет alias-expansion и дубликатов ключей.
3. HTML-экранирование всех строк, отсутствие `|safe` для входных данных, external scripts, forms, iframes и auto-links из логов.
4. Markdown-экранирование управляющих конструкций и запрет активного HTML из полей; ANSI/OSC-последовательности очищаются в CLI.
5. Query, Authorization, cookies, пароли и сырые session IDs не попадают в вывод, debug, quarantine или telemetry.
6. Выходные имена генерируются программой; path traversal, symlinks/reparse points и запись поверх входа запрещены.
7. Ни одного сетевого обращения при analyze/replay/demo; отсутствует telemetry. Offline-тест блокирует sockets.
8. Resource limits для записи, YAML, gzip, числа файлов, размера БД и временных данных.
9. Контейнер без root, с read-only input, доступом на запись только к output/workspace; приложению не нужен Docker socket.
10. Обновления зависимостей и справочников контролируемы; версия и hash входят в отчёт.

Секреты ищутся по типизированным полям и известным шаблонам. Не обещать распознавание любого неизвестного секрета в свободном тексте; поэтому свободные поля по умолчанию не сохраняются. Не хранить raw fixture с реальными секретами ради теста: использовать маркированные синтетические canary-значения.

## 16. Нефункциональные требования

Все показатели производительности — первоначальные цели для реализации, не измеренные результаты. Перед релизом опубликовать фактические результаты и характеристики стенда.

| ID | Требование | Цель и метод проверки |
|---|---|---|
| NFR-001 | Производительность | 100 000 событий ≤30 с; 1 000 000 ≤180 с на документированном Linux-стенде, 4 vCPU, 8 GiB RAM, SSD; полный analyze с JSON/Markdown |
| NFR-002 | Память/диск | Peak RSS ≤1 GiB на 100k и ≤2 GiB на 1M; суммарные рабочие файлы ≤6× распакованный вход +100 MiB на standard profile |
| NFR-003 | Повторяемость | Совпадение analysis hash при одинаковых входах; версии ОС/Python задокументированы; аналитическая семантика одинакова в CI-матрице |
| NFR-004 | Надёжность | Ни одной тихо потерянной записи; остановка/сбой не публикуют успешный результат |
| NFR-005 | Переносимость | Native CLI smoke на Windows и Linux; Docker Linux; внешняя БД не требуется |
| NFR-006 | Удобство | Подготовленный demo запускается одной командой после установки; результат объясняет ошибки без чтения исходников |

Benchmark: 1 прогрев + 5 измеренных прогонов; публиковать median, max и peak RSS, cold/warm-cache режимы отдельно. Генерация данных и установка зависимостей в timing не входят; импорт, нормализация, детекты и экспорт входят. Профиль — средняя строка около 700 bytes, фиксированный seed, доля ошибок 1%, восемь правил, около 1% событий, участвующих в алертах. HTML измерять отдельно. Для adversarial-профиля с множеством групп проверять контролируемое достижение лимита, а не обещать тот же throughput.

Hosted CI используется для smoke и регрессий; абсолютные секунды приёмки измеряются на фиксированном стенде. Отсутствие такого стенда означает, что performance gate ещё не принят.

## 17. Проверка качества и тесты

Детальная спецификация — в `TEST_PLAN.md`; каталог содержит **256 отдельных кейсов**, включая 64 кейса детектов, 20 временных проверок, 20 проверок безопасности, property-based, аварийные и нагрузочные проверки. Параметризация может дать больше запусков, но число запусков не считается числом независимых требований.

Требуемые уровни: unit, integration, scenario, property, security, end-to-end, performance, delivery. У каждого теста есть ID, вход/действие, ожидаемый результат и связь с FR/NFR. Expected values задаются отдельно от реализации; нельзя получать эталон вызовом того же детектора.

Порог покрытия: branch coverage ≥85% по пакету и ≥90% для времени, DSL, детектирования и triage. Сгенерированные модели и сторонний код исключаются с объяснением. Высокое покрытие не заменяет проверки семантики. Обязательные мутации: `>=` на `>`, удаление tenant key, смена левой границы окна, снятие redaction и HTML escape, нарушение порядка sequence. Каждая должна быть обнаружена тестами. В v1.0 достаточно такого целевого mutation-набора без общего процента mutation score.

Ни одного необъяснённого skip/xfail обязательного кейса на поддерживаемой платформе. Windows-специфичные проверки запускаются на Windows; Linux-права и signals — на Linux. Flaky-тест считается дефектом; бесконечные retries не используются.

## 18. Датасеты и честная оценка детектов

### 18.1. Три вида данных

1. Контрактные фикстуры: короткие вручную проверенные истории для точных границ, полей и evidence.
2. Синтетический replay: разные пользователи, фон, задержки, timezone, NAT, повреждения и контекст с зафиксированным seed.
3. Лабораторные записи: минимум три атаки и три легитимных процесса в принадлежащем разработчику тестовом приложении. Для этих записей сохранить конфигурацию стенда и хронологию действий. Внешние датасеты — дополнительная проверка только при подходящей схеме и достаточных метках.

Никаких реальных персональных данных или боевых паролей в GitHub. Генератор создаёт события; для performance и CI не требуется запускать инструменты атак.

### 18.2. Состав набора v1.0

- 48 базовых сценариев: 16 suspicious, 16 benign, 16 degraded/ambiguous.
- В suspicious: по два сценария на детект. К ним добавляются варианты временных границ и условий в тест-каталоге.
- В benign: ошибки владельца, password manager, NAT, разрешённое сканирование, регламентная регистрация MFA, повторная доставка, нормальные denied-ответы, тестовые аккаунты и другие пары к детектам.
- В degraded: нет user/IP/outcome/session/request ID, неизвестная зона, clock skew, часть файлов отсутствует, перепутан источник и другие ограничения.
- Train/model fitting в v1.0 отсутствует. Есть development/tuning suite и отдельный frozen evaluation suite.
- Для каждого набора — независимые шаблоны поведения; смена seed одного шаблона сама по себе не считается независимым evaluation.
- Evaluation содержит минимум 40 размеченных атакующих эпизодов и 80 benign-эпизодов; ambiguous/degraded считают отдельно. Допускается больше одного эпизода в файле. Фикстуры тестов не заменяют этот набор.

Эти числа — минимум комплектации, не статистическое доказательство эффективности в реальном SOC.

### 18.3. Манифест сценария

Обязательные поля: scenario_id, version, split, family_id, description, origin, generator_version, seed, input hashes, tenant/app, observation interval, capabilities, context hash, episode labels, expected rule IDs, expected entity keys, relevant event IDs, expected time ranges, expected quality findings, prohibited conclusions. Метки лежат вне входных событий и не доступны детектору.

Критический пример: benign-сценарий с 10 ошибками владельца обязан сработать на DET-001, если дополнительных данных нет. Эталон может требовать review, а не «ноль алертов». Нельзя обучить тесты скрывать неудобную неоднозначность.

### 18.4. Метрики

Два независимых отчёта:

**Корректность реализации:** точное соблюдение правил на контрактных фикстурах; 100% обязательных ожиданий.

**Полезность детектирования:** на frozen evaluation — precision, recall и F1; FP на 100 benign-эпизодов; алерты на 10 000 benign-событий; доля неоценённых эпизодов; case reduction; время обработки. Не называть алерты/события FPR: FPR = FP/(FP+TN) считается только при определённом наборе негативных эпизодов.

Сопоставление: алерт и эпизод совпадают по tenant/app, detector family, целевой сущности и содержат хотя бы одно ожидаемое relevant event в заявленном интервале. Один алерт сопоставляется максимум одному эпизоду, один эпизод — максимум одному алерту для primary metrics. При конкуренции выбрать максимальное число совпадающих evidence, затем минимальное расхождение времени, затем стабильный ID. Дополнительные алерты на тот же эпизод учитываются как duplicate alerts и FP первичной оценки; отдельная episode recall показывает обнаружение хотя бы раз.

Для цепочки у episode задаётся набор допустимых primary detector IDs; вспомогательные алерты считаются отдельно и не маскируют отсутствие нужной последовательности. Missing required data не исключается молча: публикуется end-to-end recall со всеми размеченными атаками и отдельный recall на eligible subset. Ambiguous-эпизоды имеют собственную таблицу решений без искусственного присвоения benign.

Предварительная цель: precision ≥0.85 и episode recall ≥0.90 на frozen eligible suite, без падения recall отдельной detector family ниже 0.80. Показывать TP/FP/FN/TN и 95% интервалы для долей; при малой выборке явно указывать ширину интервала. Эти пороги фиксируются до просмотра финальной выборки. Если они не достигнуты, публикуется результат и устраняется причина; нельзя переименовать тестовые данные ради прохождения.

### 18.5. Эксперимент, показывающий отличие

Сравнить на одной зафиксированной выборке:

- A: отдельные правила без context и сборки кейсов.
- B: правила + сборка кейсов, без context.
- C: правила + кейсы + разрешённый context + отчёт о пробелах.

Для каждого варианта измерить число алертов, кейсов, эскалаций, duplicate alerts, пропуски, FP и неоценённые эпизоды. Снижение количества кейсов не означает снижение FP. Улучшение времени работы аналитика заявляется только после отдельного пользовательского исследования; до этого можно показать число необходимых ручных переходов и конкретные примеры.

## 19. CI и поставка

На pull request: format/lint, typing, schema validation, тесты правил, unit/integration/property с ограниченным числом примеров, security, небольшой e2e, branch coverage, сборка wheel. Целевой runtime стандартного PR pipeline ≤10 минут; при превышении оптимизировать фикстуры, не удалять критические проверки.

Расширенный job вручную и перед релизом: все сценарии, больше property examples, целевые mutation-тесты, package/container smoke, benchmark, offline проверки и сверка evaluation. Не требуется создавать расписание или автоматизацию вне репозитория.

GitHub Actions: минимальные permissions, сторонние actions закреплены commit SHA, lockfile обязателен. Проверка зависимостей и секретов даёт проверяемый отчёт. Критические и высокие применимые уязвимости требуют исправления либо документированного разбора применимости; suppressions имеют срок и причину. Никаких настоящих credentials для тестов.

Поставка: wheel/sdist, Dockerfile, пример config, source manifest, правила, schemas, синтетическое demo, changelog, checksums релизных артефактов, SBOM. LICENSE и THIRD_PARTY_NOTICES фиксируются до публикации сторонних компонентов. README не содержит вымышленных значков прохождения тестов.

## 22. Основные риски и решения

| Риск | Решение |
|---|---|
| Разрастание до полноценной SIEM | Зафиксировать offline batch, восемь детектов и один основной домен |
| NAT, повторная доставка и ошибки владельца | Контекст, корректная идентичность, negative scenarios, отсутствие автоматического benign |
| Недостоверный порядок событий | UTC, точность, uncertainty и отдельный результат order_unverified |
| Красивый отчёт с необоснованными выводами | Структурированные facts/evidence/hypotheses и запрет неподтверждённой компрометации |
| Высокие метрики только на генераторе | Независимые шаблоны evaluation, лабораторные данные и честные ограничения |
| Избыточное объединение кейсов | Tenant/app границы, сильные ключи, причины рёбер и отрицательные тесты NAT |
| Исполнение содержимого логов | Ограниченный DSL, allowlist, экранирование, отсутствие сетевых переходов |
| Скрытая потеря данных | Counters, quarantine, quality report и явные partial/failed состояния |
| Неправильные теги ATT&CK | Проверенные ссылки, platform scope, кандидатный статус, допустимый пустой mapping |
