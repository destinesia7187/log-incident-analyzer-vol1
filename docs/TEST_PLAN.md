# Log Incident Analyzer — план тестирования

**Версия:** 1.0 · **Дата:** 27.09.2026

**Связанное ТЗ:** TECHNICAL_SPECIFICATION.md

**Объём:** 256 отдельных тест-кейсов, 22 группы. Все имеют статус planned.

Это спецификация будущих проверок. Здесь нет реализованных тестов и результатов их запуска. Проверка структуры данного документа не является проверкой будущего анализатора.

## 1. Правила выполнения

Каждая строка каталога задаёт самостоятельное проверяемое поведение. Given/When описывает подготовку и действие; Then — наблюдаемый результат. Тест должен проверять существенные поля и побочные эффекты, а не только отсутствие исключения.

Общие значения фикстур: tenant=t1, app=a1, user=u1; IP из документационных диапазонов 192.0.2.0/24, 198.51.100.0/24 и 2001:db8::/32; базовое время 2026-01-15T12:00:00Z. Никакой связи с настоящими пользователями. Если кейс не меняет параметр, используются пороги из ТЗ, нулевая clock uncertainty и микросекундная точность. В production-профилях точность определяется источником.

Window W: t-W < event_time <= t. Все count checks используют уникальные события после установленной дедупликации. Проверки с t-W+1us используют источник, который действительно поддерживает микросекунды. В тестах секундного источника нельзя искусственно добавлять точность.

Для каждого ID создать traceable pytest test/parametrized case либо воспроизводимый acceptance runner. ID включается в pytest node/marker или JUnit property. Файл test-cases.json содержит те же кейсы и предназначен для проверки полноты реализации. Он не является executable test suite.

Набор эталонов хранится независимо от алгоритма: вручную проверенные expected event IDs, counts, rule IDs и quality findings. Нельзя построить expected output тем же кодом, который тестируется. Snapshot допустим для структуры отчёта, но критические assertions должны проверяться отдельно.

## 3. Организация тестового кода

Рекомендуемые файлы будущего репозитория: tests/unit/test_time.py, test_dsl.py, test_normalize.py; tests/scenarios/test_det_001.py … test_det_008.py; tests/integration/test_storage.py, test_triage.py, test_quality.py, test_reporting.py; tests/security/; tests/property/; tests/e2e/; benchmarks/.

Fixture factory умеет создавать event с явным timestamp, source, tenant/app, original_id и нужными полями. Она не должна вычислять expected alert. Для временных сценариев используется фиксированный clock. Для I/O ошибок — fault injection на файловой границе; заполнение диска пользователя не требуется. Для Ctrl+C — отдельный дочерний процесс в временном каталоге. Большие лимиты проверяются unit reader doubles и отдельным реалистичным performance-run.

Обязательные markers: unit, integration, scenario, property, security, e2e, performance, delivery, windows_only, linux_only. Не полагаться на порядок выполнения. Каждый тест получает отдельный workspace и фиксированный context. Случайный seed логируется; Hypothesis сохраняет минимальный воспроизводимый пример. Регрессия превращается в постоянную fixture с описанием причины.

## 4. Как оценивать сценарий

Сценарные assertions охватывают: наличие/отсутствие rule ID; ключ сущности; eligible/excluded counts; границы evidence; severity/priority; mapping и его статус; связанные case IDs; запрещённые утверждения; состояние run и exit code.

В кейсах с несколькими одновременно работающими детектами проверяется только явно обозначенный detector и обязательные связи; остальные разрешённые срабатывания перечисляются в manifest. Отсутствие DET-002 не означает обязательное отсутствие DET-001.

Детектор должен находить подозрительную активность и в benign-сценарии, если наблюдаемые условия совпадают. Ground truth о намерении не подмешивается в runtime. Такой пример может быть корректным выполнением правила и ложным сигналом в оценке полезности одновременно.

## 5. Критические сквозные assertions

- Tenant/app границы сохраняются на каждом этапе.
- Event time и семантика окон совпадают в Python, SQL и отчётах.
- Evidence существует, имеет provenance и не содержит секретов.
- Нет автоматического вывода о компрометации по одному success, HTTP 200 или тегу ATT&CK.
- Missing/invalid данные не становятся известными значениями и не исчезают из статистики.
- Никаких внешних запросов или исполнения содержимого логов.
- Partial/failed run нельзя спутать с завершённым анализом без алертов.
- Повторяемость сравнивается по аналитическому payload, исключая операционный timestamp/duration.

## 6. Gates и отчётность

Branch coverage: ≥85% по пакету, ≥90% для времени, DSL, detection и triage. Шесть обязательных мутаций: >=→>, удаление tenant key, смена левой границы, снятие redaction, снятие HTML escaping, нарушение sequence order. Каждая должна быть поймана тестом. Число независимых требований важнее числа параметризованных запусков.

Test report содержит commit, lockfile hash, OS/Python, cases implemented/planned/passed/failed/skipped, coverage, seeds и ссылки на артефакты. Отдельно публикуются performance и detector evaluation. Нельзя писать «256 тестов пройдено», пока все 256 ID не реализованы и не выполнены в соответствующей среде.

Автоматизировать DOM/encoding-проверки HTML; клавиатурный и печатный smoke дополнить коротким ручным просмотром перед релизом. Проверка README выполняется clean-environment runner и финальным просмотром человеком. Эти ручные дополнения не заменяют машинные assertions.

## 10. Отрицательные примеры для ревью тестов

- Плохой тест: «вызвать analyze и проверить, что JSON не пуст». Нужны assertions по rule ID, evidence, counts и состоянию.
- Плохой эталон: сгенерировать expected детектором в начале того же теста. Нужен независимый ожидаемый результат.
- Плохая метрика: считать каждый benign event true negative и получить почти 100% accuracy. Нужны определённые эпизоды и знаменатели.
- Плохая регрессия: заменить snapshot после изменения порога без рассмотрения различий. Нужны diff и причина.
- Плохое исправление: скрыть шумный алерт общим исключением IP. Нужны область, срок, evidence и тест пропуска реальной атаки.
- Плохой benchmark: измерять только уже распарсенные события и назвать это скоростью полного анализа. Нужны опубликованные границы измерения.

## 11. Процедура финальной приёмки

1. Зафиксировать release candidate, lockfile, schemas, rule/context hashes и frozen suite.
2. Проверить, что каждый ID из test-cases.json соответствует реализованной проверке.
3. Выполнить CI-матрицу, все scenario/security/e2e проверки, targeted mutations.
4. Выполнить evaluation без изменения порогов после просмотра результатов; опубликовать TP/FP/FN и ограничения.
5. Выполнить нагрузочные проверки на фиксированном стенде; приложить median/max/RSS/disk и пять прогонов.
6. Проверить wheel/container из релизных артефактов, offline demo и README quickstart.
7. Открыть HTML/Markdown примеры, проверить evidence, отсутствие секретов и точность формулировок.
8. Отметить Definition of Done из основного ТЗ. При провале обязательного gate релиз v1.0 остаётся незавершённым.
